### P2：引擎-数据解耦（下一步待启动）

**目标**：将引擎层与数据库访问解耦（Repository 模式），使引擎成为纯领域逻辑层，为后续技术栈迁移、多用户扩展、数据库迁移打地基。

**一句话说明**：当前引擎函数直接接收 `conn` 参数做数据访问——这不是分层而是"分了文件夹没分职责"。解耦后引擎接收 dict、返回 dict，数据访问由 Repository 层统一负责。

#### 功能列表

| # | 功能 | 优先级 | 说明 |
|---|------|--------|------|
| 1 | Repository 层创建 | P0 | 新增 `app/repo.py`，封装全部数据访问（读规则、存处方、查患者、写预警），引擎不再直接执行 SQL |
| 2 | 引擎函数纯逻辑化 | P0 | `stratify_risk`、`determine_pattern`、`build_prescription`、`check_safety`、`evaluate_alerts` 等函数移除 `conn` 参数，改为接收参数集 dict、返回 dict |
| 3 | 规则加载重构 | P0 | 规则数据由调用方（view/Service）经 Repository 加载后传入引擎，引擎不碰 conn |
| 4 | GUI 层适配 | P0 | GUI 回调改为：经 Repository 取数据 → 调引擎纯函数 → 经 Repository 存结果，GUI 保持薄层 |
| 5 | 测试拆分 | P0 | 纯逻辑测试（构造 dict，无 DB）+ 集成测试（Repository 带 DB），现有 33 用例全部回归 0 FAIL |
| 6 | 数据库健康检查 | P1 | 启动时检查 DB 连接可用性，损坏时提示而非崩溃 |
| 7 | "database is locked" 重试 | P2 | DB 层增加简单重试逻辑（SQLite 单写者锁场景） |

#### 成功标准

- [ ] 引擎层所有公开函数签名中无 `conn` 参数
- [ ] Repository 层集中全部 SQL 访问，引擎不直接执行 SQL
- [ ] 引擎可脱离 DB 做纯逻辑单元测试（构造 dict 即可测试）
- [ ] 现有 33+ 测试全部回归 0 FAIL
- [ ] GUI 全流程（建档→评估→处方→签发→PDF→随访→预警）可正常完成

#### 前置依赖

| 风险 | 等级 | 缓解措施 |

### P3：安全合规升级（临床部署前置条件）

**目标**：达到临床部署的最低安全合规要求，满足《个人信息保护法》和等保 2.0 三级基线。

**一句话说明**：当前 XOR+base64 加密等于明文存储，无登录系统任何人开机即可访问全部患者数据——这是临床部署的硬性阻断项，不是可选改进。

#### 功能列表

| # | 功能 | 优先级 | 说明 |
|---|------|--------|------|
| 1 | 加密升级：XOR → AES-256 | P0 | 使用 Python `cryptography` 库实现 AES-256-CBC，密钥从环境变量或 OS keychain 读取，不在源码/配置文件中硬编码 |
| 2 | 密钥管理机制 | P0 | 密钥从 config.ini 迁移到环境变量（开发环境）或 OS keychain（生产环境），config.ini 只存非敏感配置 |
| 3 | 用户登录系统 | P0 | 用户名/密码 + bcrypt 哈希存储，登录会话管理（token 或 session），未登录不可访问任何功能 |
| 4 | RBAC 角色权限控制 | P0 | user 表 + role 字段（医师/治疗师/护士/管理员），UI 菜单和操作按角色显示/隐藏/限制 |
| 5 | 操作审计日志 | P0 | 独立 audit_log 表，记录所有数据访问和修改操作（who/when/what/old/new），区别于应用日志 |
| 6 | 输入范围校验 | P1 | LVEF 0-100、RPE 6-20、血压 30-300、心率 20-250 等数值字段加范围校验，异常值拦截 |
| 7 | 数据库文件保护 | P1 | 评估 SQLite + SQLCipher 全库加密方案，或文件级权限控制 |
| 8 | 登录界面 | P0 | tkinter 登录窗口，密码输入框、错误提示、会话超时 |

#### 成功标准

- [ ] 患者姓名/联系方式使用 AES-256-CBC 加密，密钥不在任何源码/配置文件中
- [ ] 未登录用户无法访问任何功能界面
- [ ] 不同角色看到不同菜单和操作权限
- [ ] audit_log 表记录所有数据访问和修改操作
- [ ] 数值字段输入超范围时拦截并提示
- [ ] 全量测试 0 FAIL（含安全相关测试用例）

#### 前置依赖

- P2 完成（Repository 层就位后，安全逻辑统一在 Service/Repository 层实现，不散落在引擎和 GUI 中）

#### 风险与缓解

| 风险 | 等级 | 缓解措施 |
|------|------|---------|
| 加密升级导致历史数据无法解密 | 高 | 提供数据迁移脚本：遍历旧数据 → XOR 解密 → AES 重新加密；迁移前自动备份 .db 文件 |
| tkinter 登录界面用户体验差 | 中 | 保持简洁，仅用户名/密码/登录按钮；会话 token 内存保存，关闭应用即登出 |
| RBAC 角色设计不当影响科室工作流 | 中 | 先实现最简角色（医师/治疗师/管理员），与科室确认后再细化 |
| 等保 2.0 合规深度超出单机能力 | 高 | 明确本阶段目标为"最低限度合规"，正式等保测评需 P4 架构演进后进行 |

#### 用户决策点

1. **角色体系设计**：需要几个角色？各角色的权限边界是什么？建议先与科室确认角色清单。
2. **密码策略**：是否需要密码复杂度要求、定期更换、锁定策略？等保 2.0 三级有具体要求。
3. **审计日志保留策略**：日志保留多久？是否需要日志防篡改？
4. **是否同步推进等保测评**：如需正式等保 2.0 三级备案，建议在 P3 完成后启动测评流程。

#### 不在范围内

- 数字签名 / CA 证书对接（正式电子签名法合规，归 P5 或独立专项）
- 数据库迁移到 PostgreSQL（归 P4）
- 多用户网络架构（归 P4）
- 患者端认证（归 P5 患者端开发）

#### 用户决策点（关键决策——决定后续所有工作形态）

1. **技术栈路线选择**（本阶段最核心决策）：

   - **路线 B：FastAPI + React/Vue Web 应用** — 天然多用户、远程访问、Playwright 测试、响应式布局。需要前后端分离开发、部署服务器。适合：院外随访/多科室协作/多中心推广。
   - **路线 C：继续 tkinter + 局部修补** — 不迁移技术栈，仅补图表库（matplotlib 嵌入）和手动测试流程。适合：短期内不扩大使用，仅课题结题/演示用途。
2. **部署架构选择**：单院内网部署 vs 云端部署 vs 混合部署？
3. **是否引入外部开发资源**：用户是中医研究生，架构演进阶段可能需要专业开发支持（学校医工交叉研究院合作 / 外包）。
4. **数据库选择**：PostgreSQL（功能全）vs MySQL（普及度高）vs 继续 SQLite + WAL 模式（小规模多用户）？

### P5：临床生态集成（长期，按需推进）

**目标**：实现与院内信息系统及患者端的数据互通，打通心脏康复全程管理闭环。

**一句话说明**：这个阶段依赖外部接口文档和合作方配合，不能臆造接口、不能写死模拟数据。按临床价值优先级分步推进。

#### 功能列表

| # | 功能 | 优先级 | 说明 |
|---|------|--------|------|
| 1 | 可穿戴设备数据接入 | P0 | 心脏康复 II/III 期核心需求——居家康复期间自动采集心率、步数、运动数据。对接微信运动或厂商 API |
| 2 | HIS 对接 | P0 | 接收患者基本信息、手术记录、出院带药，避免重复录入。需医院信息科接口文档和审批 |
| 3 | 消息推送 | P1 | 随访提醒、康复指导推送、预警通知（短信/微信），提高患者依从性 |
| 4 | LIS 检验结果对接 | P1 | 自动获取 BNP、肌钙蛋白、血脂、糖化等检验结果用于评估 |

- [ ] 可穿戴设备心率/步数数据可自动回传系统并参与预警判定

- P4 完成（多用户架构 + 技术栈迁移完成——患者端和外部集成需要服务端 API 支持）
- 外部接口文档：
  - HIS 对接 → 医院信息科提供接口文档和审批

#### 风险与缓解

| 风险 | 等级 | 缓解措施 |
|------|------|---------|
| 医院 HIS 接口审批周期长（数月） | 高 | 提前启动信息科沟通；P5 其他功能可并行推进 |

#### 用户决策点

1. **HIS 对接方式**：接口直连 vs 视图只读 vs 中间表？需与信息科确认可行方案。
2. **可穿戴设备选型**：对接微信运动（零成本但数据粗）vs 专业心率带/手表厂商 API（数据精但需合作）？
3. **消息推送渠道**：短信（成本但到达率高）vs 微信公众号/小程序消息（免费但依赖患者关注）？

5. **伦理审查启动时机**：涉及患者数据院外传输和采集，需提前启动伦理申请。

- 多中心 / 医联体数据汇总（远期规划，需 P5 完成后评估）
- AI 辅助证型判读（远期研究课题）
- 区域级数据看板（远期规划）

## 三、优先级理由

### 业务价值 × 技术风险矩阵

| 阶段 | 业务价值 | 技术风险 | 价值-风险比 | 排序理由 |
|------|---------|---------|------------|---------|
| **P1 工程基础** | 中（稳定性提升） | 低（修补性工作） | 高 | 阻断性问题优先解决，已完成 |
| **P2 引擎解耦** | 高（后续所有扩展的地基） | 低-中（引擎质量 A 级，重构可控） | 最高 | 解耦后引擎可纯逻辑测试、可迁移数据库、可换技术栈——是 P3/P4/P5 的前置条件 |
| **P3 安全合规** | 高（临床部署硬性要求） | 中（安全模式成熟，但数据迁移有风险） | 高 | 不解决安全问题不能上临床，是 P4/P5 的前置条件 |
| **P4 架构演进** | 高（科室级部署条件） | 高（技术栈迁移，GUI 重写） | 中 | 价值高但风险也高，必须在 P2 解耦后进行（否则引擎也要改） |
| **P5 临床集成** | 高（全程管理闭环） | 高（外部依赖，不可控因素多） | 中 | 临床价值最高但依赖外部接口和合作方，放最后 |

### 排序逻辑

1. **P2 先于 P3**：解耦是安全升级的前置——安全逻辑（加密、RBAC、审计）应统一在 Repository/Service 层实现，而非散落在引擎和 GUI 中。不解耦就做安全升级，等于在不稳固的地基上盖楼。

2. **P3 先于 P4**：安全合规是临床部署的硬性阻断项（法律要求），技术栈迁移是效率/扩展性问题。先解决"能不能用"再解决"好不好用"。

3. **P4 先于 P5**：患者端和外部系统集成需要服务端 API 支持，单机 tkinter 架构无法支撑外部集成。必须先完成多用户架构和技术栈迁移。

4. **P5 排最后**：依赖外部接口文档和合作方配合，不可控因素最多。但可以提前启动前置工作（伦理审查、信息科沟通、接口调研）。

### 关键路径

```
P1(✅完成) → P2(待启动) → P3(安全升级) → P4(架构演进) → P5(临床集成)
                                         ↑
                                    用户决策点：技术栈路线
```

> **注意**：P2-P3 之间没有硬性顺序依赖（P3 的安全功能可以在未解耦的架构上实现，只是不够优雅）。但建议 P2 先行，因为解耦后 P3 的工作量和风险都会显著降低。如时间紧迫，P2 和 P3 可部分并行。
