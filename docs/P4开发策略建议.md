> **文档定位**：本文件是对 `docs/分阶段开发设计与任务列表.md` 第五章（P4：架构演进）的**策略层修正与补充**。原文档给出了技术选型矩阵和框架级任务列表，本文件补充：决策逻辑、风险重估、启动时机、开发方法。两者配合使用——原文档回答"怎么做"，本文件回答"什么时候做、为什么这么做、避什么坑"。

## 1. 核心判断

**P4 的技术栈选择是部署形态问题，不是技术问题。** 先定"给谁用、怎么用"，再选 PySide6 还是 Web。拿技术矩阵去反推业务是倒置的——技术矩阵只能帮你评估"某条路线能不能满足需求"，不能替你决定"你要不要满足那个需求"。

---

## 2. 对原 P4 方案（技术设计文档第五章）的三点修正

### 修正一：P4-T1「选型报告 + 原型，3-5 天」→ 压缩为「决策备忘，半天」

选型本质是一个**业务决策**："是否扩大使用、以什么形态使用"。技术矩阵已经在原文档 5.1 节列全了（10 维度），缺的是决策，不是原型验证。建议把 T1 改为《P4 路线决策备忘》（模板见 `docs/P4开发设计文档.md` §1），由用户（Lenci）填写部署形态并签字确认路线，不预写技术原型。HerMES 不需要花 3-5 天搭原型去证明"PySide6 能画图表"——这已被无数项目验证过。

### 修正二：真正的风险在 T2（GUI 重写），不在 T3（数据库迁移）

| 任务 | 原估工作量 | 真实风险 | 说明 |
|------|-----------|---------|------|
| T3 多用户 + PostgreSQL 迁移 | 1 周 | **低** | P2 的 Repository 解耦已把数据访问收敛到 50 方法接口后。换 PG = 再写一个实现同一接口的 `PostgreSQLRepository` + `repo_factory`，引擎 612 行一行不动。**这是 P2 解耦的直接回报，P4 里最便宜的部分** |
| T2 GUI 层重写（6 视图） | 1-2 周 | **高** | GUI 零测试是当初 4 个 P1 bug 的根因。把 tkinter 视图重写到 PySide6/React，是新 P1 bug 的高发区。应作为 P4 的重点风控对象，而非 T3 |

> 原文档把 DB 迁移和 GUI 重写并列，容易让人误以为"换数据库最难"。实际相反——**P2 已经把最难的部分（引擎与数据解耦）做掉了**，剩下的 DB 迁移只是接口实现的复制粘贴。

### 修正三：路线 C（继续 tkinter + matplotlib 补丁）建议否掉

原文档将路线 C 列为"短期课题结题/演示"的可选项。但若非只要一张 demo 截图，不应选。理由：matplotlib 能补**图表**能力，但补不了**可测试性**——而可测试性缺失正是 4 个 P1 bug 的根因。路线 C 等于把技术债原样保留，只贴了张图表创可贴。

## 3. 技术栈推荐（按部署形态分叉）

| 你的部署形态 | 推荐路线 | 理由 |
|------------|---------|------|
| 只有你自己用 / 课题答辩演示 / 单台机器 | **A：PySide6 桌面** | 拿到图表（Qt Charts）+ 可测试性（QtTest）+ 打包（PyInstaller），部署模型不变，单人最易维护。Web 对单人研究生是过度工程 |
| 有真实医院科室要多人共用 / 要做院外远程随访（II/III 期） | **B：FastAPI + React Web** | 多用户在桌面程序上硬做 = 手搓一套 C/S 同步协议，比直接用 Web 技术难得多。Web 天然多用户 + 远程访问，心脏康复院外随访正中靶心 |
| 纯 demo、不真实使用 | C：tkinter + matplotlib | **仅限此场景，否则否** |

**决策口诀**：单人用→PySide6；要多人/远程→Web；别在 tkinter 上打补丁。

---

## 4. 反向建议：现在不要启动 P4

这是本文件最想强调的一点。项目定位是 MVP / 课题，P3（安全合规）还需用户做"是否扩大使用"的决策。合理的节奏是：

```
P3 完成 → 系统已是「安全、单机、AES 加密、RBAC 保护」的临床决策支持工具
        → 这是完整、可答辩的课题成果
        → 暂停架构投资，转做临床内容（更多病种配置、规则调优、导师验证）
        → 等出现真实部署信号（某家医院说"我们要用"）再启动 P4
```

现在就投 2-4 周做 P4 基础设施，与当初"7 个病种建空壳只启用 1 个"是同一类错误——**premature abstraction（过早抽象）**。基础设施建好却无人使用 = 白烧几周。把这几周花在临床实质内容上，对课题与论文贡献更大。

等部署需求真的来了，P4 的栈选择反而一目了然（医院内网多人→PySide6 或服务端；要远程随访→Web），且 P2 的 Repository 已把迁移成本压到最低。

## 5. 若确定启动 P4：垂直切片法（非大爆炸重写）

1. **选栈**（决策备忘，半天）
2. **只挑 1 个最简单视图**（患者管理）端到端移植：新 GUI + Repository + 引擎全链路跑通 + 写该视图自动化测试。这一步是"证明新架构能 work"的探路，故意选最便宜的视图
3. **其余 5 视图逐个移植**，每个都保持现有 76 个测试全绿
4. **最后做 DB 迁移**（仅 Web 路线）——因 P2 解耦，这步最稳

> 这样系统始终可运行，且栈特有的坑（Qt 信号槽 / React 状态管理）在第一个视图就暴露，不会到第五个视图才爆。

## 6. 与 P2 / P3 的关系

| 关系 | 说明 |
|------|------|
| P2 → P4 | P2 引擎-数据解耦是 P4 可行的前提。引擎纯逻辑化后，P4 迁移时引擎 612 行不动，只换 Repository 与 GUI 层 |
| P3 → P4 | P3 安全升级（RBAC/认证）是 P4 多用户架构的前置。P4 的 API 层需直接复用 P3 的 `AuthManager` |
| 启动时机 | 取决于 P3 的"扩大使用"决策。决策为"否"则 P4 暂不启动；决策为"是"且有具体部署形态，则按 §3 选路线启动 |
