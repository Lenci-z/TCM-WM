> 项目：中西医结合心血管康复方案包与数字化全程管理系统
> 分析日期：2026-08-03
> 分析范围：系统整体架构决策与技术选型（非代码级 bug，详见《代码验收报告》）
> 分析基础：全部 15 个 .py 源文件 + 6 个 JSON 种子文件 + 2 个测试文件 + 设计文档 v0.2 逐行审查

## 〇、结论摘要

引擎层（612 行）设计严谨、质量为 A 级。但系统整体的架构决策——**tkinter + SQLite 单机 + XOR 加密 + 无认证**——这三条组合在一起，意味着如果要走向真实临床场景，不是迭代能解决的，需要架构层面的重新决策。

| 维度 | 当前状态 | 临床部署要求 | 差距等级 |
|------|---------|-------------|---------|
| 引擎领域逻辑 | 优秀 | 正确 | ✅ 无差距 |
| 数据安全 | XOR 玩具级 | AES + 认证 + 审计 | 🔴 严重 |
| 多用户能力 | 单机独占 | 科室共享 | 🔴 需重写数据层 |
| GUI 可测试性 | 零覆盖 | 医疗软件必须 | 🔴 技术栈限制 |
| 临床生态集成 | 完全孤立 | HIS/可穿戴/消息推送 | 🟡 缺失但可后补 |
| 工程规范 | 无依赖管理/迁移/配置 | 最低限度可运维 | 🟡 快速可补 |

**定位判断**：如果项目目标为 MVP 原型 / 概念验证 / 课题结题演示，当前架构完全够用。如果目标为科室实际部署，建议在投入更多功能开发前先做架构评审。

## 一、技术栈选型：tkinter 做医疗软件是错配

### 1.1 问题概述

tkinter 作为 Python 标准库 GUI 工具包，适合快速原型和简单工具，但在医疗软件场景下存在结构性缺陷。

### 1.2 具体缺陷

| 缺陷 | 临床影响 |
|------|---------|
| 无原生图表组件 | 康复随访核心需求是画趋势图（HR 变化、6MWD 进展、RPE 趋势），ttk.Treeview 只能列表格，画不了折线图。当前随访管理完全依赖数值表格，无法直观展示康复进展 |
| 无可测试性 | **最致命问题**。tkinter 无 DOM、无 accessibility tree，无法被 Selenium/Playwright 类工具驱动。4 个 P1 bug 全部在 GUI 层且全部漏测，根本原因即在于此 |
| 无原生打印支持 | 临床场景需要直接打印处方，当前只能绕道 reportlab 生成 PDF 再手动打印，多一步操作且依赖外部库 |
| 无主题/无障碍支持 | 临床环境对对比度、字体大小有要求（老年医师、长时间使用），tkinter 主题系统几乎等于没有 |
| 无安装包方案 | 每台临床机器需安装 Python 3.13 + 全部依赖，没有 freeze/installer 策略。临床 IT 部门不会接受这种部署方式 |
| 无多显示器支持 | 临床医师常用双显示器（一边看病历一边看处方），tkinter 对此支持极弱 |

### 1.3 替代方案对比

| 方案 | 优势 | 劣势 | 适用场景 |
|------|------|------|---------|
| PyQt/PySide | Qt Charts 原生图表、QtTest 测试框架、pyinstaller 打包、主题系统成熟 | 授权复杂（PyQt GPL/商业，PySide LGPL）、学习曲线陡 | 需要桌面客户端的科室级应用 |
| Web（FastAPI + React/Vue） | 天然多用户、远程访问、Selenium/Playwright 测试、响应式布局 | 需要前后端分离开发、需部署服务器 | 需要院外随访/多科室协作的场景 |
| Electron + Python 后端 | 跨平台桌面 + Web 技术栈测试能力 | 体积大、内存占用高 | 对 UI 交互要求高的场景 |

**建议**：如果保持桌面定位，迁移到 PySide6；如果接受 Web 化，FastAPI + React 是最面向未来的选择。

## 二、单机架构是扩展死胡同

### 2.1 当前架构

```
┌─────────────────────────────────┐
│  单台临床电脑                    │
│  ┌───────────┐  ┌────────────┐  │
│  │ tkinter   │→ │ SQLite     │  │
│  │ GUI 进程  │  │ .db 文件   │  │
│  └───────────┘  └────────────┘  │
│       ↑                          │
│  单人操作，数据不离开本机         │
└─────────────────────────────────┘
```

### 2.2 问题分析

**数据孤岛**：患者数据存在一台机器上。康复科多个治疗师/医师无法共享患者档案。主任无法查看全科研复进展统计。

**SQLite 单写入者限制**：即使想做简单的多终端共享（比如 NFS 共享数据库文件），SQLite 的单写入者锁机制会导致频繁的 "database is locked" 错误。

**无备份策略**：SQLite 文件损坏 = 全部数据丢失。当前没有任何备份/恢复机制。临床数据丢失是安全事故。

**无远程访问**：心脏康复 II 期/III 期核心在院外。患者出院后需要远程随访、居家康复指导、可穿戴设备数据回传——单机桌面系统完全无法支撑。

**无系统级审计**：虽然应用内记录了临床操作日志，但谁在什么时候打开了数据库文件、谁复制了文件——这些系统级操作无记录。

### 2.3 扩展路径

从单机到多用户不是"加个网络层"，而是数据访问层整体重写：

| 阶段 | 改造内容 | 工作量估计 |
|------|---------|-----------|
| 第一步 | 数据库从 SQLite 迁移到 PostgreSQL（服务端部署） | 中 — SQL 语法差异小，但 DAO 层需全量审查 |
| 第二步 | GUI 与数据库之间增加 API 服务层（FastAPI） | 大 — 等于在 GUI 和 DB 之间插入一整层 |
| 第三步 | GUI 改为调用 API 而非直连数据库 | 中 — 每个 engine 函数的 conn 参数都要去掉 |

**关键点**：当前引擎函数直接接收 `conn` 参数，这个设计决定了迁移成本——每个引擎函数的签名都要改。

## 三、分层名义上分离，实际上耦合

### 3.1 声称的架构 vs 实际的架构

**声称的分层**：
```
UI 层  →  Engine 层  →  DB 层
（界面）  （领域逻辑）  （数据存取）
```

**实际的调用关系**：
```
assessment_view.py   ──→  engine.stratify_risk(conn, ...)     ──→  conn.execute("SELECT ... FROM disease_config")
prescription_view.py ──→  engine.build_prescription(conn, ...) ──→  conn.execute("SELECT ... FROM rule_rx_template")
patient_view.py      ──→  db.query(conn, "patient", ...)       ──→  conn.execute("SELECT ... FROM patient")
```

引擎层函数直接接收并使用 `conn`（数据库连接对象），意味着引擎层在做数据访问。这不是分层，是"分了文件夹但没分职责"。

### 3.2 具体后果

**引擎无法脱离数据库做单元测试**：当前测试代码需要先建临时 DB、导入种子数据，才能测试引擎函数。如果引擎接收的是 domain object（dict/dataclass），测试只需构造字典即可。

**GUI 层做领域决策**：`assessment_view.py` 第 290/332 行硬编码 `"CAD_PCI"`、`prescription_view.py` 第 201 行硬编码 `"CAD_PCI"`——这些本应由引擎从患者档案读取，现在由 UI 层决定。

**换数据库要改引擎代码**：如果从 SQLite 迁移到 PostgreSQL，`conn.execute()` 的占位符从 `?` 变成 `%s`，所有引擎文件都要改。

### 3.3 正确的分层

```
UI 层   →  Service 层  →  Repository 层  →  DB 层
（界面）   （编排+事务）  （数据访问）       （连接池）
               ↓
          Engine 层
         （纯领域逻辑，接收 dict，返回 dict）
```

引擎层应只接收数据结构、返回数据结构，不碰 `conn`。数据访问由 Repository 层负责，事务管理由 Service 层负责。

## 四、安全架构有实质性合规风险

### 4.1 风险总览

| 风险项 | 严重程度 | 当前状态 | 合规要求 |
|--------|---------|---------|---------|
| 患者数据加密 | 🔴 严重 | XOR+base64，密钥硬编码在源码 | 《个人信息保护法》要求加密存储敏感个人信息；等保 2.0 三级要求 AES-256 + 密钥管理 |
| 用户认证 | 🔴 严重 | 无登录系统，开机即可访问 | 医疗信息系统必须具备身份认证 |
| 角色权限 | 🔴 高 | 无 RBAC，所有用户权限相同 | 医师/治疗师/护士/管理员需不同权限 |
| 签发真实性 | 🔴 高 | `signed_by` 为文本字段，无数字签名 | 电子签名法要求可靠的电子签名 |
| 数据库文件保护 | 🟡 中 | .db 文件可被直接拷走 | 需文件级加密或数据库级加密 |
| 操作审计 | 🟡 中 | 仅应用内临床操作有记录 | 需系统级审计日志 |

### 4.2 XOR+base64 "加密"详解

当前实现（`db.py`）：
```python
# 密钥硬编码在源码中
_KEY = 0x5A

def encrypt_text(text):
    return base64.b64encode(bytes([b ^ _KEY for b in text.encode()])).decode()

def decrypt_text(cipher):
    return bytes([b ^ _KEY for b in base64.b64decode(cipher)]).decode()
```

问题：
1. **XOR 单字节密钥**：只有 256 种可能，暴力破解 < 1 毫秒
2. **密钥在源码中**：任何拿到 .py 文件或 .pyc 文件的人可以提取密钥
3. **Base64 不是加密**：只是编码，任何人可以解码
4. **无完整性校验**：攻击者可以篡改密文，系统无法检测

这意味着患者姓名和联系方式在数据库中实际上是**明文存储**——任何能访问 .db 文件的人，用 Python 两行代码就能"解密"全部数据。

### 4.3 合规差距

| 法规/标准 | 相关要求 | 当前合规状态 |
|-----------|---------|-------------|
| 《个人信息保护法》第 51 条 | 采取相应加密、去标识化等安全技术措施 | ❌ 不合规 |
| 《数据安全法》第 27 条 | 建立健全全流程数据安全管理制度 | ❌ 不合规 |
| 等保 2.0 三级 | 身份鉴别、访问控制、安全审计、数据完整性、数据保密性 | ❌ 5 项全不达标 |
| 《电子签名法》第 13 条 | 可靠的电子签名需专有控制 | ❌ 文本框输入不构成电子签名 |

### 4.4 升级路径

**最低限度（可快速实施）**：
1. 加密升级：XOR → AES-256-CBC（Python `cryptography` 库），密钥从环境变量读取
2. 增加登录系统：用户名/密码 + bcrypt 哈希
3. 增加 RBAC：user 表 + role 字段 + UI 菜单按角色显示/隐藏

**正式部署（需架构调整）**：
1. 密钥管理：OS keychain 或 HSM
2. 数据库加密：SQLite + SQLCipher，或迁移到 PostgreSQL + 透明数据加密
3. 数字签名：对接 CA 证书实现真正的电子签名
4. 审计日志：独立的 audit_log 表，记录所有数据访问和修改操作

## 五、测试架构有结构性盲区

### 5.1 覆盖率分析

```
当前测试路径：
  test_engine.py  →  engine.函数(conn, ...)  →  断言返回值
  test_e2e.py     →  engine.函数(conn, ...)  →  断言返回值 + PDF 文件

实际用户路径：
  用户操作  →  tkinter 事件  →  GUI 回调函数  →  engine.函数(conn, ...)  →  GUI 更新
```

**两条路径的前半段完全不同。** e2e 测试虽然名为"端到端"，但实际绕过了整个 GUI 层。

### 5.2 后果

4 个 P1 bug 全部在 GUI 层且全部漏测：

| Bug | 位置 | 漏测原因 |
|-----|------|---------|
| P1-1 Entry.set() 崩溃 | patient_view.py:177 | GUI 事件回调从未被测试触发 |
| P1-2 simpledialog 未导入 | prescription_view.py:320 | 同上 |
| P1-3 保存字段不完整 | prescription_view.py:298 | 同上 |
| P1-4 consecutive_met 未实现 | alerts.py | 引擎测试未覆盖该操作符 |

### 5.3 根因

tkinter 无法被自动化测试——没有 DOM 树、没有 accessibility interface、没有官方测试框架。这不是"补测试"能解决的，是技术栈选择带来的结构性限制。

### 5.4 对比

| 技术栈 | GUI 测试方案 | 成熟度 |
|--------|-------------|--------|
| tkinter | 无官方方案，需 hack（LDTP/pyautogui） | 极低，不可靠 |
| PyQt/PySide | QtTest 模块 | 成熟，可模拟事件 |
| Web（React/Vue） | Selenium / Playwright / Cypress | 极成熟，行业标准 |

## 六、多病种架构是过早抽象

### 6.1 现状

设计文档明确标注"v0.2: 架构宽、数据窄，仅 CAD_PCI 启用"。数据库中 7 个病种条目，6 个为空壳。

### 6.2 问题

**YAGNI 违反**（You Aren't Gonna Need It）：
- 每张业务表都有 `disease_category` 字段
- 每个引擎函数都要处理 disease_category 维度
- 每个 GUI 表单理论上都要考虑多病种（虽然现在硬编码了）
- disease_config 用 JSON blob 存储，无法做 DB 级查询和完整性校验

**全链路复杂度代价**：增加了所有层的认知负担，但只服务了 1 个病种。

**未来风险**：当第二个病种（如心力衰竭）真正到来时，心衰的评估流程可能跟 CAD_PCI 根本不同：
- 不同的评估量表（NYHA 分级 vs SYNTAX 评分）
- 不同的分层逻辑（可能不是简单的高/中/低）
- 不同的处方结构（可能需要利尿剂管理、容量监测）

现有的"换 JSON 参数"抽象未必 fit。到那时要么硬塞进现有框架（别扭），要么重构（浪费之前的抽象）。

### 6.3 建议

如果短期内不会新增第二个病种，建议：
1. 保留 disease_category 字段（零成本预留）
2. 移除空壳病种条目（减少认知噪音）
3. 等第二个病种需求明确时再评估抽象是否需要调整

## 七、工程基础设施缺失

### 7.1 缺失清单

| 缺失项 | 后果 | 修复成本 |
|--------|------|---------|
| 无 requirements.txt | 新人/临床 IT 不知道要装 reportlab，跑不起来 | 低 — 5 分钟 |
| 无数据库迁移机制 | v0.3 加字段时现有患者数据无法平滑升级（init_db 只 CREATE IF NOT EXISTS，不 ALTER） | 中 — 需引入 Alembic 或自建迁移脚本 |
| 无配置文件 | 数据库路径、加密密钥、医院名称（PDF 页眉）全硬编码 | 低 — 增加 config.ini 或 .env |
| 无日志系统 | 引擎返回 None 静默失败，GUI 弹窗但不记录，出问题无法追溯 | 中 — 引入 logging 模块 + 日志文件轮转 |
| 无错误恢复策略 | DB 被锁/文件损坏时直接崩溃，无回退方案 | 中 — 需要全局异常处理 + 数据库健康检查 |
| 无 test/\_\_init\_\_.py | 部分测试发现工具可能不识别 test 包 | 低 — 1 分钟 |
| 无 CI/CD | 代码变更无自动测试验证 | 中 — 需配置 GitHub Actions 或类似方案 |

### 7.2 数据库迁移问题详解

当前 `init_db()` 逻辑：
```python
CREATE TABLE IF NOT EXISTS patient (...);
```

问题：如果 v0.3 需要给 patient 表加 `phone2` 列，`CREATE IF NOT EXISTS` 不会执行（表已存在），新列不会被添加。

现有数据库升级的唯一方式是手动执行 ALTER TABLE，或者删库重建（丢失所有患者数据）。

**建议**：引入 schema_version 表 + 迁移脚本：
```python
# migration_001_to_002.py
def upgrade(conn):
    conn.execute("ALTER TABLE patient ADD COLUMN phone2 TEXT")
```

## 八、临床生态孤立

### 8.1 现状

系统完全自包含，无任何外部系统集成。

### 8.2 缺失集成

| 集成需求 | 当前状态 | 临床价值 |
|---------|---------|---------|
| HIS 对接（接收患者基本信息） | ❌ 手动录入 | 避免重复录入、减少录入错误 |
| CPET 设备数据导入 | ❌ 手动录入 | 有 CPET 数据时自动计算峰值 VO₂、AT 等指标 |
| 可穿戴设备（心率带/手表） | ❌ 无 | 居家康复期间自动采集心率、运动数据 |
| 消息推送（短信/微信） | ❌ 无 | 随访提醒、康复指导推送，提高患者依从性 |
| 检验系统（LIS）对接 | ❌ 无 | 自动获取 BNP、肌钙蛋白等检验结果用于评估 |
| 心电图/超声报告 | ❌ 无 | 获取 LVEF、室壁运动等数据用于分层 |

### 8.3 优先级建议

1. **最高优先**：可穿戴设备数据接入——心脏康复 II/III 期的核心需求
2. **高优先**：HIS 对接——减少重复录入是科室接受系统的前提
3. **中优先**：消息推送——提高随访依从性
4. **低优先**：LIS/心电图对接——数据量小，手动录入可接受

## 九、错误处理架构

### 9.1 现状

| 层 | 错误处理方式 | 问题 |
|----|-------------|------|
| 引擎层 | 返回 None 或空 dict | 静默失败，调用方需要判断 None，容易遗漏 |
| GUI 层 | messagebox.showerror | 只弹窗不记录，无法追溯 |
| DB 层 | 无 try-except | SQLite 异常直接传播到 GUI |
| 全局 | 无 | 无顶层异常捕获，未处理异常直接闪退 |

### 9.2 建议架构

```
GUI 层：try-except 捕获 → messagebox 提示用户 + logging.error 记录
Service 层：事务回滚 + 自定义异常（如 PatientNotFoundError）
Engine 层：返回 Result 对象（success/failure + data/error_msg）而非 None
DB 层：连接池 + 重试逻辑（处理 "database is locked"）
全局：sys.excepthook 兜底 + 崩溃日志
```

## 附：架构优势（不应忽视的亮点）

本报告聚焦问题，但以下设计决策值得肯定，在重构时应保留：

1. **规则外置到数据库**——不硬编码任何阈值/模板/禁忌，引擎统一读库。这是正确的领域建模，重构时应保留。
2. **缺数据保守判高危**——医疗安全取向正确，符合临床思维。
3. **医师签发不可跳过**——合规意识到位，"临床决策支持工具"定位准确。
4. **矩阵编码（A1-F3）**——将复杂的证型×分层组合简化为可索引的编码，便于处方模板管理和检索。
5. **无 CPET 处方路径**——RPE 主导 + HRR 校验的设计具有实际临床价值，解决了基层医院无 CPET 设备的痛点。
6. **预警闭环设计**——触发→处置→关闭留痕，符合医疗安全事件管理规范。
