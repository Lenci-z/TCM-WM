## 3. 路线 B：FastAPI + React Web（多人 / 远程随访）

### 3.0 三端拆分与开发优先级（2026-08-03 用户决策）

**背景**：用户确认"后续科室使用"→ 路线 B（Web）基本锁定；患者端暂不开发。因此路线 B 按**三端**组织，先排优先级再排任务。

| 端 | 承载内容 | 使用频率 | 优先级 |
|----|---------|---------|--------|
| **医师端** | 患者管理、评估录入、处方生成/签发、随访管理、预警处理、规则库维护 | 每天高频 | **P0（优先开发）** |
| **管理端** | 用户/角色管理、数据看板、审计日志、备份 | 低频治理性 | P1（后置） |
| **患者端** | 处方查看、随访打卡、八段锦视频 | 院外 | **暂不开发**（依赖医师端产出数据） |

**决策：医师端优先**，理由：
1. **业务闭环全在医师端**：建档→评估→分层→处方→签发→随访→预警，系统存在的全部理由
2. **数据源头在医师端**：管理端看板/审计是"消费"医师端产生的数据，消费端不该先于生产端建设
3. **管理端 Python 层 P3 已铺好**：用户/角色/RBAC/审计/备份逻辑已实现，Web 化主要是界面重写，无先行紧迫性
4. **部署第一天刚需**：科室上线即需建档/评估/开处方；账号分配是初始化一次性动作（P3 init admin 已支持）

**边界修正**：规则库维护（处方模板/预警规则/八段锦分级）的真正调整者是科室负责人/质控医师，**归入医师端**（高级医师权限），不属纯管理端。管理端只保留：用户管理、数据看板、审计日志、备份。

**医师端内部顺序（垂直切片）**：患者管理 → 评估 → 处方 → 随访 → 预警，每步可测、可验收。

## 5. 风险与缓解

| 风险 | 等级 | 缓解 |
