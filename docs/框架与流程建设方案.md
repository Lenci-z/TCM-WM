## 一、背景与定位

架构评审（Ada）指出：引擎层 A 级无差距；差距集中在技术栈选型（tkinter 单机）、安全合规、测试盲区与工程基础设施。评审给出的定位判断为"MVP 原型 vs 科室部署"二分。

**用户决策口径**：不做二分——系统后面总归要扩大使用；**当前阶段的关键是框架搭建与流程建设**。因此：

- 不启动阶段二安全升级（AES/登录/RBAC，等真正扩大使用时再做）
- 不启动 Web 化迁移（技术栈决策保留到扩大使用前评估）
- **现在做**：① 工程流程建设（低风险，立即受益）② 框架分层搭建（引擎与数据访问解耦，为扩大使用打地基）

### 步骤 2｜框架搭建（后续执行，核心工程）

对应架构报告 §三：引擎与 DB 解耦（Repository 模式）

- 新增 Repository 层（`app/repo.py`）：封装全部数据访问（读规则、存处方、查患者）
- 引擎函数改为**纯领域逻辑**：接收参数集 dict、返回 dict，**不接 `conn`**
- 规则加载由调用方（view/Service）经 Repository 完成
- 收益：① 扩大使用（Web/多用户）时只换数据访问层，引擎逻辑不动 ② 引擎可脱离 DB 做纯逻辑单测
- 不动 UI 技术栈（tkinter 保留）

### 步骤 3｜测试对齐（跟随步骤 2）

- 引擎单测拆分：纯逻辑测试（构造 dict，无 DB）+ 集成测试（Repository 带 DB）
- 现有 33 用例全部回归 0 FAIL

## 三、明确不做（本次及近期）

| 项 | 理由 |
|---|---|
| AES 加密 / 登录 / RBAC / 审计 | 扩大使用前做（阶段二），当前无多用户场景 |
| Web 化 / PyQt 迁移 | 技术栈决策保留，扩大使用前评估 |
| 移除 6 个空壳病种条目 | 与设计文档 v0.2 第 5.1 节硬约束冲突，**不采纳** |
| HIS / 可穿戴 / 消息推送集成 | 需外部接口文档，按需推进 |
