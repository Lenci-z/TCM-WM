## 5. 遗留问题（P2 未闭合项）

### 🔴 P1：`delete_patient` 级联删除不完整

**位置**：`app/repo.py` line 273-279

```python
def delete_patient(self, patient_id: int) -> None:
    """删除患者（含手术信息）。
    注意：patient 表无 ON DELETE CASCADE，需手动删 procedure。
    """
    self.conn.execute("DELETE FROM procedure WHERE patient_id=?", (patient_id,))
    self.conn.execute("DELETE FROM patient WHERE patient_id=?", (patient_id,))
    self.conn.commit()
```

**问题**：`db.py` 开启了 `PRAGMA foreign_keys=ON`，共有 **10 张子表**通过外键引用 `patient`：

| 子表 | 外键位置（db.py） |
|------|-----------------|
| procedure | line 96 |
| assessment | line 111 |
| tcm_pattern | line 145 |
| risk_stratification | line 159 |
| prescription | line 172 |
| adherence_log | line 200 |
| vital_upload | line 214 |
| alert | line 225 |
| follow_up | line 242 |
| clinical_event | line 255 |

当前 `delete_patient` 只删了 `procedure`，删一个有评估/处方/预警记录的患者会触发 `IntegrityError` 崩溃。

**这是上一轮审核报告已指出的 P1 级 bug，本轮 T4/T5 收尾未修复。** docstring 写明"需手动删 procedure"，但实现者只处理了 procedure，未处理其余 9 张子表。

**影响**：删除任何有真实诊疗记录的患者会崩溃。当前无测试覆盖该场景（`test_delete_patient` 只测了无子记录的患者）。

**修复建议（供 Hermes 下一轮执行）**：

```python
def delete_patient(self, patient_id: int) -> None:
    """删除患者及其全部子表记录。
    外键已开启，须先删子表再删父表，否则 IntegrityError。
    """
    children = [
        "procedure", "assessment", "tcm_pattern", "risk_stratification",
        "prescription", "adherence_log", "vital_upload", "alert",
        "follow_up", "clinical_event",
    ]
    for tbl in children:
        self.conn.execute(f"DELETE FROM {tbl} WHERE patient_id=?", (patient_id,))
    self.conn.execute("DELETE FROM patient WHERE patient_id=?", (patient_id,))
    self.conn.commit()
```

并补测试：创建含 assessment + prescription + alert 的患者 → 调 `delete_patient` → 断言 4 张表均清空。

## 9. 更正记录（Ada 误判声明，2026-08-03）

### 9.1 误判声明

本轮审核（第 5 节 B-1）将 `delete_patient` 判定为"级联删除不完整的 P1 bug"并建议"补 9 张子表级联 DELETE"——**该判定有误，特此更正**。

**误判依据**：复核 `test_repo.py` 的 `test_delete_patient_with_records_blocked`（docstring 明确"保护性设计：有业务记录的患者删除被拒绝（IntegrityError），且数据不丢失。医疗数据不可级联删除"）——这证明实现者（Hermes）不是漏改，而是**有意设计**为"保护性拒绝"：有诊疗记录的患者不删，靠外键约束保证数据不丢。

**真实问题**（更正后）：保护逻辑**依赖底层外键异常隐式实现**——repo 层直接调用会抛 `IntegrityError`（语义不明确），若调用方未捕获即崩溃。

**修复方向**（更正后）：**显式保护式拒绝**——`delete_patient` 显式检查业务记录，有记录抛明确的 `ValueError("…拒绝删除（医疗数据保护）")`；GUI 捕获后友好提示。**撤回**"补 9 条 DELETE 级联删除"建议（那会推翻合规设计）。

### 9.2 更正后状态（Hermes 已按更正方向修复，提交 `6ba41ab`）

| 项 | 更正后实现 |
|----|-----------|
| `repo.delete_patient` | 显式检查 9 张诊疗子表（assessment/tcm_pattern/risk_stratification/prescription/adherence_log/vital_upload/alert/follow_up/clinical_event）；有记录抛 `ValueError`（含表名与条数）；procedure 属建档信息随患者删除不拦截；无记录正常删 |
| `patient_view._delete` | 确认框说明"有业务记录将拒绝删除"；`except ValueError` 捕获后 `showwarning` 提示"医疗数据保护：有业务记录的患者不可删除"；成功/拒绝均写日志 |
| `test_repo` | `test_delete_patient_with_records_blocked`：造 6 类业务记录 → `assertRaises(ValueError)`（含"拒绝删除"文案）→ 患者/评估/处方/随访数据完好断言 |
